# Contributing to Awesome BUNX

Thank you for your interest in contributing to Awesome BUNX! This document provides guidelines for
contributing to this curated list of JavaScript / TypeScript CLI tools runnable via `bunx` or `npx`.

## Adding a New Tool

To add a new CLI tool to the list:

1. The tool must be installable from the npm registry
2. The tool must be runnable via `bunx <package>` (or equivalently `npx <package>`)
3. The tool should have credible support and remain useful on its documented platforms
4. The tool should be useful for a general audience
5. The tool should offer a clear capability or practical advantage over existing entries

Assess support in context: mature, stable, or feature-complete tools do not need frequent
releases. Explain the tool's distinct value, documented invocation, supported platforms, and
material prerequisites such as accounts, payment, credentials, or external services.

Use official documentation and registry metadata to qualify a proposal. Treat installation and
a meaningful CLI invocation as separate validation, following this repository's checks before
acceptance. Do not claim that metadata or a successful installation alone proves runtime behavior.

GitHub stars may help prioritize research among otherwise suitable candidates. There is no minimum
star count, and popularity alone does not determine addition, retention, replacement, or removal.
Do not disadvantage niche tools, new projects, non-GitHub hosting, or packages in shared monorepos.

### Updating, Replacing, or Removing a Tool

Prefer the smallest correction that restores usefulness: update commands, package names, URLs,
prerequisites, descriptions, or version guidance before proposing removal.

A removal needs a specific, corroborated reason that keeping the entry would mislead or poorly
serve users, such as confirmed package unavailability, persistent failure on a supported platform,
misleading package identity, explicit retirement affecting continued use, or a material unresolved
security problem that cannot reasonably be addressed by an upgrade or usage correction.

Archival, feature completeness, old releases, quiet development, low stars, or a more popular
competitor alone do not justify deletion. Defer when evidence is insufficient, and distinguish
temporary outages or unsupported environments from defects in the tool.

For a replacement, verify the successor and compare essential functionality, platform coverage,
prerequisites, migration costs, and lost capabilities. Explain what users gain and lose, with
evidence and estimated maintainer effort. Choose an explicit outcome: retain, update, replace,
remove, or defer.

### Required Information

Each tool entry needs:

- A unique package name (as it appears on npm)
- A brief, clear description
- A link to its documentation or repository
- A list of executable commands the package installs

Release metadata (`version` and `last_release`) is generated by automation. Please do not add or
edit those fields in pull requests.

### Where to Edit

All tool data lives in a single file at the root of the repository: **`tools.json`**.

The file has a top-level `"categories"` array. Find the category that best fits your tool and add
an entry to its `"tools"` object. If no existing category fits, you can propose a new one (see
below).

### JSON Format

```json
{
  "categories": [
    {
      "name": "Category Name",
      "slug": "category-slug",
      "tools": {
        "your-package-name": {
          "description": "Brief description of the tool",
          "url": "https://link-to-documentation-or-repo",
          "execs": ["executable1", "executable2"]
        }
      }
    }
  ]
}
```

**Field reference:**

| Field         | Required | Description                                                   |
| :------------ | :------: | :------------------------------------------------------------ |
| `description` | yes      | One-line description of what the tool does                    |
| `url`         | yes      | Link to official docs or repo (`http://` or `https://` only)  |
| `execs`       | yes      | Non-empty list of binary names installed by the package       |
| `examples`    | no       | List of example objects (see below)                           |
| `version`     | no       | Generated by automation; do not edit in community PRs         |
| `last_release`| no       | Generated by automation; do not edit in community PRs         |

> **Tip:** The package name key is what gets passed to `bunx <package>`. If the binary name
> differs from the package name (e.g. package `@biomejs/biome` installs binary `biome`), make sure
> `execs` reflects the actual binary name and the examples use the explicit form:
> `bunx --package <package> <binary>`.

### Adding Examples

The `examples` field is optional but encouraged when the invocation is non-obvious — for example
when the package name differs from the binary, a subcommand is needed, or a specific flag is
required to do anything useful.

Each example is an object with a required `cmd` and an optional `description`:

```json
"your-package-name": {
  "description": "...",
  "url": "...",
  "execs": ["binary-name"],
  "examples": [
    {
      "cmd": "bunx your-package-name --some-flag",
      "description": "What this example does"
    }
  ]
}
```

**Example field reference:**

| Field         | Required | Description                                        |
| :------------ | :------: | :------------------------------------------------- |
| `cmd`         | yes      | Full shell command the user can copy and run       |
| `description` | no       | One-line explanation of what the command does      |

Guidelines for writing good examples:

- Prefer `bunx <package>` when the binary matches the package name
- Use `bunx --package <package> <binary>` when the binary differs from the package name
- Commands also work with `npx` — pick whichever runner you prefer for examples
- Prefer short, realistic commands over exhaustive flag lists
- Add multiple examples only when they demonstrate meaningfully different use cases

### Choosing a Category

Choose one existing category based on the tool's primary purpose. Categories reflect this npm
catalog; they do not need to match the Python or Rust lists.

- **Scaffolding & Generators** covers project starters and source-file generators. A
  framework-specific starter can also fit **Frontend Frameworks & Tools** when grouped with its
  framework's CLI; explain that choice in the PR.
- **Frontend Frameworks & Tools** covers framework development, build, and component workflows.
- **Version Control & Git** covers commit conventions, Git hooks, and release automation tied to
  Git, including `commitizen` and `semantic-release`.
- **Package Management** covers dependency inspection, upgrades, and package cleanup.

Keep category-only reorganizations separate from adding tools. When two categories fit, explain
the main use case in the PR. Preserve existing category slugs when changing display names so
README links keep working.

### Adding a New Category

If your tool doesn't fit any existing category, add a new object to the `"categories"` array:

```json
{
  "name": "Human Readable Name",
  "slug": "url-friendly-slug",
  "tools": { ... }
}
```

Keep the slug lowercase, hyphen-separated, and consistent with the name.

## Pull Request Process

1. Fork the repository
2. Create a new branch for your changes
3. Edit `tools.json` to add your tool to the appropriate category
4. Run `bun run scripts/checks.ts` locally to validate your changes
5. Run `bun run scripts/readme.ts` and commit the regenerated `README.md`
6. Run `bun run scripts/readme.ts --check` and `bun test`
7. Make sure all checks pass
8. Create a pull request with a clear description of the tool you're adding

GitHub Actions validates the catalog, tests the maintenance scripts, and checks README freshness
on relevant pull requests and pushes. Ordinary validation is read-only and reports a stale
README rather than rewriting it. The separate **Validate Installs** workflow tests newly added packages
via `bunx` on catalog pull requests. It reports failures in job summaries and artifacts without
commenting on or approving the PR.

### Choosing a Pull Request Template

Use the template that best matches your change:

- [Add a new tool](https://github.com/carlosferreyra/awesome-bunx/compare/main...main?quick_pull=1&template=add-tool.md)
- [Update existing tool metadata](https://github.com/carlosferreyra/awesome-bunx/compare/main...main?quick_pull=1&template=update-tool.md)
- [Repo maintenance or refactor](https://github.com/carlosferreyra/awesome-bunx/compare/main...main?quick_pull=1&template=repo-maintenance.md)

Choose your branch as the compare branch after opening the link. If none of these fit, use the
default PR template and explain the change clearly.

## README Generation and Release Sync

`README.md` is generated from `tools.json` and `template/README.md.j2`. Edit those source files,
then regenerate the README rather than editing it directly. Package examples are displayed in
collapsible blocks below their category tables.

```sh
# Validate the catalog
bun run scripts/checks.ts

# Regenerate the README
bun run scripts/readme.ts

# Check freshness without rewriting files
bun run scripts/readme.ts --check

# Test maintenance scripts without installing catalog tools
bun test
python3 -m unittest discover -s tests -v
```

Release sync runs every Monday at 06:00 UTC or manually on `main`. It validates the catalog,
fetches npm release metadata, regenerates and checks README, and publishes `tools.json` and
`README.md` together. Sync runs are serialized and create no commit when nothing changes.
A concurrent update to `main` causes a normal push failure; rerun sync against the latest main.

If any npm lookup fails, the script retains that package's previous metadata and exits
unsuccessfully. Successful lookups are saved locally, but the workflow does not publish a
partial result. You can run the script manually with `bun run scripts/latest_release.ts`.

## Validation Checks

Your contribution will be automatically checked for:

- Required fields (`description`, `url`, `execs`)
- Valid URL format (must start with `http://` or `https://`)
- Non-empty executable list
- Valid JSON structure
- Successful installation and invocation via `bunx`

## Validation Workflow Structure

All three catalogs separate fast checks from installation work:

- **Validate Catalog** (`ci.yml`) runs on relevant PRs, pushes to `main`, and manual requests.
  It validates the catalog, runs maintenance-script tests, and checks generated README freshness.
  The job has a 20-minute timeout and does not install catalog packages.
- **Validate Installs** (`validate_installs.yml`) performs package installation checks separately.
  Manual runs accept an optional `base_ref`: leave it empty for the full catalog, or provide a
  Git ref to select newly added package names relative to that commit. Changes to existing
  entries and examples still need targeted maintainer validation.
- Both validation workflows use read-only repository permissions, discard checkout credentials,
  write an Actions summary even after failure, and upload available failure logs for 14 days.
  Missing/partial reports are shown as incomplete; they are not treated as successful coverage.
  Validation never approves or merges PRs and does not require permission to post comments.

UVX and Bunx run install checks automatically for relevant PRs and run a full check on the
first day of each month at 00:00 UTC. Their install jobs have a 30-minute timeout.

A green installation check is limited to the probes implemented by the ecosystem validator;
it does not prove every documented command or platform works. Use meaningful fixtures before
accepting a candidate. Job timeouts and permission failures require inspecting the logs; they
do not by themselves establish that a catalog tool is broken.

Release-metadata publication keeps this repository's existing behavior and schedule.
